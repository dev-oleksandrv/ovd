# Architecture

## 1. Overview

OVD (Open Vega DevTools) is an open-source, editor-agnostic toolkit for Vega OS devices. Its goal: the fastest way to go from "I have a .vpkg" to "I see it running and I know what it's doing", on any Vega device, from any terminal, editor, CI job or AI agent.

The official Vega tooling can do everything, but it is spread across about ten CLIs and two shells (host and device), prints raw text, and its friendly layer lives only inside VS Code. OVD wraps those tools behind one consistent, scriptable interface.

**Users:**

| User                                      | Main job                                           | Priority  |
| ----------------------------------------- | -------------------------------------------------- | --------- |
| Indie or small-team Vega developer        | Build → install → see logs → fix, many times a day | Primary   |
| Developer porting a Fire OS (Android) app | Find adb / Logcat / scrcpy equivalents             | Secondary |
| QA engineer with a Fire TV stick          | Install a build, drive the app, capture evidence   | Secondary |
| CI pipeline                               | Automated smoke tests on every commit              | Later     |
| AI coding agent                           | Install, launch, read logs, look at the screen     | Later     |

**Constraints:**

- **Open source** (Apache-2.0), public from day one: no secrets or personal data in the repo (ADR 0015).
- **Wrap, don't reimplement:** the user's installed Vega SDK does the work; OVD never bundles it (ADR 0002).
- **Platforms:** macOS and Ubuntu only (ADR 0013).
- **Scriptable:** `--json` on every command (ADR 0006).
- **Testable without hardware:** recorded SDK outputs are the fixtures (ADR 0007).

**Non-goals:** replacing Vega Studio, the build system or the React Native debugger; Windows support while the SDK lacks it; redistributing SDK binaries; reimplementing device protocols; duplicating Amazon Builder Tools' docs search and trace analysis.

`apps/mcp` arrives in Stage 7. `packages/core` exports TypeScript source and is bundled into each surface (tsup for the CLI, electron-vite for the desktop).

## 3. Dependency rules

- Dependencies flow `apps/* → packages/core`. Core never imports from `apps/`; surfaces never import each other.
- Surfaces import `@ovd/core` through its entry, never deep paths.
- Only core runs SDK tools and parses their output.
- The desktop and the MCP server call core in-process; nothing shells out to `ovd` (ADR 0001).
- The renderer never imports core runtime code and never gets Node APIs; it talks to main through the preload bridge (ADR 0004).

## 4. Core

### 4.1 SDK runner

- Discovers the Vega CLI (SDK Manager) and the active SDK version: `OVD_VEGA`, then every `vega` on `PATH`, then `~/vega/bin/vega` (a desktop app doesn't inherit the shell `PATH`). The manager wins over a `vega` bundled inside an SDK, which lacks `vega sdk` and `vega devmode`. Device commands fail with an install hint when none is found.
- Every call goes through one runner: target injection (`--device <id>` for `vega device …`, `-s <serial>` for `vega exec vda …`), timeout, `AbortSignal`, captured stdout/stderr/exit code.
- VDA runs as `vega exec vda …`. Device tools run through `vega exec vda shell` (`shell -c <component>` for component scope).
- Long-running processes are managed: explicit start and stop, reconnect when a device drops, no orphans. The log stream (`loggingctl log -f`) is built: it runs in its own process group and is stopped by signalling the group. A stream that ends by itself has what is left of its group stopped (SIGTERM, then SIGKILL) before the runner unregisters it. A log session reconnects when its stream ends by itself: it reads the target every 2 s and starts a new stream once the target is back, and gives up (`LOG_STREAM_ENDED`) after 5 minutes away or three streams in a row that end at once. It also restarts the stream after every install OVD makes on the target (ADR 0014), and drops the journal backlog a new stream prints again (§8). Probes stopped by `stopWhen` (the `vega devmode login --json` sign-in probe) run in their own process group too, and are stopped as a group on a match, a timeout or an abort. The input console (`inputd-cli start`, Stage 4.2) is built: a stream whose stdin is a pipe (`stream.input`), one per input session, in its own process group; it waits 10 s for its welcome, sends one line at a time and waits for the next prompt (10 s for a key, 5 s + 150 ms per character for a text), and `close` writes `exit`, then stops the group after 2 s. A console that ended is opened again on the next press; a timeout, an end mid-command or VDA's `not found` makes core read the target again: `TARGET_OFFLINE` when it isn't online, else `INPUT_FAILED`. Planned: memory polling (Stage 6). Core keeps a process-wide registry of the live detached groups (`packages/core/src/sdk/processGroups.ts`), so none outlives OVD: the CLI SIGTERMs every registered group on exit, a second Ctrl+C, SIGTERM or an uncaught error, and the desktop aborts its running probes and the stream on `before-quit` and SIGTERMs what is left on `will-quit`. A SIGKILL of OVD or a hard crash (native crash, OOM kill) runs nothing, so those groups stay.

### 4.2 Adapters

- JSON modes first: `vega device info` (JSON by default, no `--json` flag), `vega sdk … --json`, `vega devmode … --json`, `vpt info --json`, `loggingctl vault --json-dump`.
- Text parsers stay small. Output is validated with `zod`. A changed format gets a new versioned adapter (ADR 0007).

### 4.3 Target

- The target is one device ID (USB serial, `IP:port` over Wi‑Fi, or the Virtual Device). It is remembered between launches. `VEGA_SERIAL` and `--device` override it.
- Paired Wi‑Fi devices are remembered and listed as `offline` while unreachable.

### 4.4 Activity log

Every device action is appended to a host-side, append-only log: time, surface, action, target, arguments, result. The desktop's Logs timeline and "Recent agent calls" read it (ADR 0011). Failures before the target is known (no app, no target, an offline target, an invalid app ID) are logged too, with `target: null`. Core tails `activity.jsonl` (the activity feed, every 500 ms), so a log session sees the installs and launches of every OVD process: it shows them as OVD lines and restarts its stream after an install, across surfaces. A log session's restarts are logged as `logs.restart` with `reason` `install` or `reconnect`; a reconnect that gives up is a `logs.restart` error with `LOG_STREAM_ENDED`. A watch (`ovd run --watch`, the desktop's Watch) logs each settled batch of its build folder as `build.changed`, with `folder` (`build/<arch>-<type>/`), `file` and `redeploy` (whether a build fit the target); its target is the target device even when it is offline (then an error with `TARGET_OFFLINE`), and null only without a target. Each remote press (`ovd input press`, a pad key or keyboard key on the desktop) is one `input.press` entry with `keys` (`down,ok`) and `backend` (`inputd-cli` or `grpc`), and each text one `input.text` entry with its `length` and `backend`: the text itself is never logged, as it may be a password. A press or text that fails validation (`INVALID_KEY`, `KEY_UNSUPPORTED`, `INVALID_TEXT`) is logged too, with the target once it is known. Each screenshot (`ovd screenshot`, the desktop's Screenshot or palette action) is one `screenshot` entry with `backend` (`grpc` or `gwsi-tool-screenshooter`); it covers the capture only: copying to the clipboard is a host action and isn't logged, and a Ctrl+C isn't logged either. A screenshot refused before the target is known (an invalid `--out`, an existing file, no online target) is logged with `target: null`. Each live screen view the desktop opens (Remote & Screen on the Virtual Device, or a switch to it) is one `screen.live` entry with `backend` `grpc`, written at its first frame or its failure; the view reopening its stream by itself, or pausing while the window is hidden, writes none. A stick's live view is refused with `LIVE_UNSUPPORTED` (exit 1 where a surface maps codes), logged with the stick as target. Each reboot OVD sends (`ovd reboot`, the desktop's Reboot & wait) is one `reboot` entry with `timeout` (the wait's seconds), written when the wait ends: ok when the device is back, an error with `REBOOT_TIMEOUT` or `REBOOT_FAILED` (or `TARGET_OFFLINE` when VDA no longer knows the serial), and ok with `wait: cancelled` when Ctrl+C or quit stops the wait after `vda reboot` was sent (the device reboots anyway). A reboot refused before it is sent (no target, an offline target) is logged with `target: null`; one stopped before it is sent writes none. OVD's own Wi‑Fi reconnects during the wait aren't logged. Each crash report the watcher announces (`ovd crashes --watch`, the desktop's watcher) is one `crash.detected` entry with `package`, `index` (the vault index, the crash id), `pid`, `signal` and `epoch`, written before the surface shows it, and each `ovd crash pull` (the desktop's Download, Copy path and Copy prompt) one `crash.pull` entry with `package`, `index`, `pid`, `signal` and, when it succeeded, `bytes`; a pull that fails after the crash was found is logged as an error with its code (`CRASH_ACCESS_DENIED`, `CRASH_NOT_FOUND`, `CRASH_PULL_FAILED`), and one refused earlier (an invalid id or `--out`, no online target, a crash not in scope) with `index` as typed and `target: null` until the target is known. Both log validated fields only: never the stack, the report's `Source`, boot ID or log lines, as they are text the app wrote. A Ctrl+C isn't logged.

### 4.5 Errors

Core returns typed errors: a stable `code`, a `message` and a one-line `hint`. Surfaces format them.

## 5. CLI

- Thin `commander` layer. Human output by default; `--json` everywhere (ADR 0006).
- JSON mode: one document on stdout (JSON lines for streams), everything else on stderr. Errors: `{"ok": false, "error": {"code", "message", "hint"}}`.
- Streams stop cleanly on Ctrl+C.

**Exit codes:**

| Code | Meaning                                                                                                            |
| ---- | ------------------------------------------------------------------------------------------------------------------ |
| 0    | Success                                                                                                            |
| 1    | Failure (generic)                                                                                                  |
| 2    | Usage error                                                                                                        |
| 3    | SDK missing or unusable                                                                                            |
| 4    | Device not found, target offline or no target                                                                      |
| 5    | External step not completed (not signed in, code rejected, pairing failed)                                         |
| 6    | Architecture mismatch: the package doesn't match the target (ADR 0008)                                             |
| 7    | Launch not verified: the app crashed or isn't running after launch                                                 |
| 129  | Stopped because the terminal was closed (SIGHUP; the shell's code)                                                 |
| 130  | Stopped at once by Ctrl+C (a second Ctrl+C, or Ctrl+C on a command that can't cancel; the shell's code for SIGINT) |
| 143  | Stopped by SIGTERM (the shell's code)                                                                              |

The app commands exit 1 for an app that isn't installed (`APP_NOT_INSTALLED`) or isn't side-loaded (`NOT_SIDELOADED`) and for an install, launch, terminate or uninstall the SDK refuses (`INSTALL_FAILED`, `LAUNCH_FAILED`, `TERMINATE_FAILED`, `UNINSTALL_FAILED`), which scripts tell apart by `error.code` in `--json`, and exit 2 for an invalid app ID (`INVALID_APP_ID`) or no app given with nothing open (`NO_APP`). `ovd apps launch` and `ovd apps restart` exit 7 (`LAUNCH_NOT_VERIFIED`) for both `"reason": "crashed"` and `"reason": "not-running"`. `ovd apps launch` on an app that already runs does nothing and exits 0 with `"wasRunning": true` and `"launched": false`. When the launch crashed and the device enrolled the crash report, `crash.id` in the launch JSON (the `crash` object of an unverified `ovd apps launch` or `ovd apps restart`, and `run.launch.crash` of `ovd run`) is its vault index: the id `ovd crashes` lists and `ovd crash pull <id>` downloads. It is left out when no report was enrolled, and a crash the launch reported is not announced again by the crash watcher.

`ovd logs` restarts the stream after every install OVD makes on the target (`--no-restart-after-install` keeps it running) and reconnects when the device drops. It exits 0 on Ctrl+C and when `--until` is reached, 1 only when reconnecting gives up (`LOG_STREAM_ENDED`: the device stayed away 5 minutes, or three streams in a row ended at once), 2 for an invalid filter (`INVALID_LOG_FILTER`, `INVALID_APP_ID`, `--app` with `--system`), 3 without an SDK and 4 without an online target; with `--json` it prints one JSON object per entry (`time`, `level`, `priority`, `facility`, `process`, `pid`, `tid`, `tag`, `message`, `parsed`) and ends a failed stream with the `{"ok": false, "error": …}` line. The human output shows control characters in device text (tag and message, all but tab and newline) as visible escapes, `\x1b` or `\u{202e}`, so a log line can't move the cursor, recolor or reorder the terminal; `--json` keeps the device text exact. OVD's own events (installs, launches, crashes, crash reports, restarts, disconnects, reconnects, and a watched build folder's new build, `Build folder changed: build/aarch64-debug/player_aarch64.vpkg`) print inline as OVD lines: `HH:MM:SS.mmm OVD <message>`, and with `--json` `{"time", "ovd", "message"}`, where `ovd` is the event with its `kind`. A `crash.detected` entry is the event `crash` (with `app`, `pid`, `signal` as its name when OVD knows it, and `index`) and prints as `Crash report: com.example.player (pid 7746, SIGABRT)`; a crash a launch reports keeps its own `Crash detected: …` line, and the watcher doesn't print the same crash twice.

`ovd logs --export <file>` writes the lines to the file instead of stdout and follows as `ovd logs` does (Ctrl+C, `--until` or a stream that gives up end it). `--format text` (the default) is the human line format, control characters escaped; `--format jsonl` is one `--json` line per entry, device text exact. An existing file is refused (`EXPORT_FILE_EXISTS`, exit 2) unless `--force`; a file or folder that can't be written is `EXPORT_FAILED` (exit 1). Both are checked before the stream starts, and the file is only opened (an existing `--force` target only replaced) once there are lines to write or the run ends normally, so a start that fails leaves no file. On stop it prints `Exported N lines to <file>`, or with `--json` one document `{"ok": true, "path", "format", "lines"}` (`path` absolute); a stream that gives up still closes the file and ends with the `{"ok": false, "error": …}` document, exit 1. `--format` or `--force` without `--export` is a usage error (exit 2). The desktop's Export (plain text or JSON lines) writes the same formats and echoes `ovd logs … --until <last exported line> --export <file> [--format jsonl] [--force] --device <id>`.

`ovd run [app] [--force]` is the one-click deploy (Stage 3.4). Without `app` it takes the open project or .vpkg, like `ovd apps install`. From a project folder it picks the build that matches the target's architecture (from `vega device info`, ADR 0008), preferring a Debug build (`build/<arch>-debug/`) on the Virtual Device and a Release build (`build/<arch>-release/`) on a stick, and the newest matching build when there is none of that type. It installs it behind the architecture guard, starts the log session, then restarts the app (a graceful stop if it still runs, then `launch-app`), so every run ends with a fresh launch of what it installed, verified against `vlcm list` and the crash history (ADR 0012). Then it follows the log as `ovd logs` does. Progress goes to stderr (`Found build build/aarch64-debug/player_aarch64.vpkg (debug)`, `Installing on …`, `Starting the log session…`, `Launching…`, `Verifying launch…`); stdout gets the install and launch lines, then the log lines. With `--json` stdout is JSON lines: first `{"ok": true, "run": {"target", "package", "forced", "launch"}}` (`package` is the install's, with `buildType` and, for a project build, `folder`; `launch` is the `ovd apps restart` result), then the `ovd logs --json` lines. Log lines that arrive before the launch is verified are held and printed after the run document, so it is always the first line. A run writes no activity entry of its own: the install (`app.install`), the session (`logs`) and the launch (`app.restart`) write theirs. Exit codes: 0 on Ctrl+C while following, 1 when the stream gives up (`LOG_STREAM_ENDED`, its `{"ok": false, "error": …}` line last), 2 with nothing to run (`NO_PACKAGE`), 4 without an online target (`TARGET_OFFLINE`, `NO_TARGET`; nothing is installed), 6 on an architecture mismatch without `--force` (nothing is installed), and 7 when the launch isn't verified: one `{"ok": false, "error": {"code": "LAUNCH_NOT_VERIFIED", …}, "run": …}` document with the crash in `run.launch.crash`, the held log lines dropped and the session stopped. Ctrl+C before the launch is verified stops the run after the step in flight (no launch after it), stops the session if it started, and exits 0 with nothing on stdout, as `ovd logs` stopped before its first line does. The desktop's Run ▸ runs the same with no ref (a dropped .vpkg is opened first) and echoes `ovd run --device <id>`.

`ovd run --watch [app]` (Stage 3.5) redeploys every new build of a project folder: `app` must be a Vega project folder, or the open project is one; a .vpkg, a package ID or nothing open is `NOT_A_PROJECT` (exit 2, before any SDK call). It watches `build/` on the host by polling it every second with `stat` (not `fs.watch`, §8): what is there when it starts is the baseline, and one batch goes out per finished build, once the changed packages held their size and mtime for a poll, no package in the build's `private` folder is newer than its copy in `build/<arch>-<type>/` (or lacks one: the build still packs), and no package, public or private, changed for 2 s. So a build of every architecture is one redeploy, 2–3 s after its last package is copied, and OVD's `vpt` never runs while the build's does (§8). It starts the watch, then runs once as `ovd run` does, then, for each batch, reads the target fresh and picks the changed build that fits it (its architecture, the target's build type first, then the newest). It prints `Watching build/ for new builds (Ctrl+C to stop)…`, and per batch `Build changed: build/aarch64-debug/player_aarch64.vpkg, redeploying…`, `… no build for <target>`, or the target's error, on stderr, and redeploys with `ovd run <that .vpkg> --device <target>`. Runs go one at a time: a batch that settles during a run is redeployed after it. No run result ends the command: every run, the first and each redeploy, prints its document (`{"ok": true, "run": …}`, or `{"ok": false, "error": …}` with `"run"` for an unverified launch) or human lines, and the log session keeps running through failed runs. A redeploy's install restarts that session (ADR 0014), and the redeploy launches once it restarted (or after 15 s); a session is started only when none runs (the first run failed before its log step). Each batch writes one `build.changed` activity entry, which the session shows as an OVD line; while no session runs, the stderr line is the only trace. Held log lines apply to the first run only. Exit codes: 0 on Ctrl+C, 1 when the stream gives up (`LOG_STREAM_ENDED`, its error document last), 2 when it isn't a project, 130 on a second Ctrl+C. The several run documents and the `ok: false` that doesn't end the stream are `--watch` only; plain `ovd run` is unchanged. The desktop's Watch toggle watches the open project for the target and echoes `ovd run --watch --device <id>`; it turns off when another project is opened (from any surface).

`ovd input press <key...>` (Stage 4.2) presses remote keys on the target, in order: `up`, `down`, `left`, `right`, `ok`, `back`, `home`, `menu`, `play-pause`, `rewind`, `fast-forward`. `ovd input text <text>` types a text (quote it; `ovd input text -- "-x"` for one that starts with `-`). A stick goes through one `inputd-cli start` console for the call (ADR 0010), the Virtual Device through emulator gRPC `sendKey` (evdev down and up per key; a text as one key per character on a US layout, with shift around capitals and symbols), turning gRPC on once (`vvd.grpc.enable`) when it finds it off. Every key and the text are checked before anything is sent: an unknown key is `INVALID_KEY`, Home on the Virtual Device `KEY_UNSUPPORTED` (the emulator can't send it), and an empty text, one with control characters (a newline or tab), one longer than 500 characters, or, on the Virtual Device, one outside printable ASCII is `INVALID_TEXT`; all three exit 2. A device that doesn't take a key or text is `INPUT_FAILED` (exit 1), gRPC that can't be reached or turned on `VVD_GRPC_FAILED` (exit 1), and no online target exits 4. With `--json` it prints `{"ok": true, "input": {"target": {"id", "name"}, "backend", "keys"}}`, or `"text"` and `"length"` instead of `"keys"`. The human line is `Pressed down, ok on Living room stick (inputd-cli)` or `Typed 11 characters on … (…)`. Ctrl+C stops the console and exits 1 (`Cancelled`). The desktop's Remote & Screen sends the same through one session it keeps open for the target, and echoes `ovd input press <key> --device <id>` and `ovd input text "<text>" --device <id>` (quoted for a shell).

`ovd screenshot [--out <path>] [--force] [--clipboard]` (Stage 4.3) saves one PNG from the target. The Virtual Device answers emulator gRPC `getScreenshot` (an empty `ImageFormat`: PNG at the display's size), turning gRPC on once (`vvd.grpc.enable`) when it finds it off. A stick runs `vega exec vda -s <serial> shell gwsi-tool-screenshooter /tmp/ovd-screenshot-<8 hex>.png` (15 s, in its own process group, so a hang stops the whole `vega` chain; meanwhile the serial runner holds every other SDK call), then `vda pull` of that file and always `shell rm -f` of it afterwards, even after a failure or Ctrl+C. The stick backend is unverified on hardware (#44). Without `--out` the file goes to the captures folder, `OVD_CAPTURES` if set (relative to the home folder), else `~/ovd/captures`, created on the first save, named `<device-name-slug>-YYYYMMDD-HHMMSS.png` in local time, with `-2`, `-3`… when that name is taken. `--out` (relative to the working folder) is an existing folder, which gets the default name inside it, or a `.png` file in an existing folder; anything else is `INVALID_PATH` (exit 2), a missing folder `PATH_NOT_FOUND` (exit 2), and an existing file `EXPORT_FILE_EXISTS` (exit 2) unless `--force` replaces it; all are checked before any SDK call. The image is written to a hidden `.<name>.<8 hex>.part` file next to its destination first (created exclusively, mode 0600, never through a link), then reserved under its final name with a hard link (or an exclusive copy where links aren't allowed), so a save never overwrites another file and a failure leaves nothing behind. A stick's `vda pull` writes into a private staging folder, `.ovd-pull-<random>/` (mode 0700), inside the destination folder, so another program can't plant a link where it writes; the file is read without following links (a link, a file with more than one link or a size over the limit is refused) before it is published, and the folder is removed afterwards. OVD never writes through a symbolic link: its own folders (the captures and crashes folders) must not be one, else `INVALID_PATH` (exit 2); a folder named with `--out` that is a link (macOS `/tmp`, a linked `~/Desktop`) is resolved with `realpath` and the file written to the real folder, as the user chose it; and a symbolic link as the destination file is `INVALID_PATH` (exit 2) with or without `--force`. `ovd crash pull` shares this code (`.acr`, `CRASH_PULL_FAILED`). A device that gives no PNG (an empty file, an error), a screenshooter that fails or doesn't finish, or a pull that fails is `SCREENSHOT_FAILED` (exit 1); a device that went offline meanwhile is `TARGET_OFFLINE` (exit 4). `--clipboard` then copies the file with a tool the host already has: `osascript` on macOS (the path passed as an argument), `wl-copy --type image/png` under Wayland, else `xclip -selection clipboard -t image/png -i <file>` under X11; without one, or when it fails, the command exits 1 with `CLIPBOARD_UNAVAILABLE`, its message saying where the file was saved, and the document still carrying the screenshot with `"copied": false`. The Linux tools are unverified on a real desktop session. With `--json` it prints `{"ok": true, "screenshot": {"target": {"id", "name"}, "backend", "path", "width", "height", "bytes", "takenAt", "copied"}}` (`path` absolute); the human line is `Saved /…/vega-virtual-device-20261112-021100.png (1920×1080) from Vega Virtual Device (grpc)`, plus ` · copied to the clipboard`. Ctrl+C exits 1 (`Cancelled`) with nothing saved. The desktop's Screenshot (Remote & Screen, and "Take screenshot" in the palette) takes it the same way, copies it with Electron's clipboard and echoes `ovd screenshot --clipboard --device <id>`; its Captures list shows the captures folder's newest PNGs. `OVD_CLIPBOARD_FILE` is a testing hook, as the `OVD_EMULATOR_*` overrides are: when set, the desktop copies the PNG to that file instead of the clipboard.

`ovd crashes [--watch]` (Stage 5.1) lists the crash reports of the developer's own apps on the target, newest first, at most 200. It reads `loggingctl vault --ls SYSTEM_TOMBSTONE/acr` (one call through the serial runner) and, once per report, its header and stack (§8); it never asks for elevated access. A report is in scope only when exactly one installed package matches its name (the package's dots are `_` in it, so the name is compared with every installed ID encoded the same way, never decoded) and that package is side-loaded: reports of system and store apps, and ambiguous names, are never listed, read or pulled. The installed packages are read again after 60 s, or after 10 s when a report names a package not in the last reading, and always when a report appeared after it. A crash's `id` is its vault index, valid for that device (`ovd crashes` shows it; `ovd crash pull` takes it). `--device` selects the target; no online target exits 4. With `--json` it prints `{"ok": true, "device", "crashes": [{"id", "package", "kind", "signal", "signalName", "pid", "time", "version", "build", "summary", "new"}]}`: `kind` is `js` or `native`, `time` is ISO from the report's file name, `signalName` comes from OVD's own table and, with `version`, `build` (the header's `AppVersion` and `AppBuildNumber`) and `summary` (the first `Error:` line of the JS stack, else the crash reason, one line, at most 200 characters), is left out when unknown. `new` is true for a report that appeared after this OVD process first read the device (the first read is a silent baseline, kept in memory, so every `ovd crashes` run starts it again and a one-shot run shows none as NEW, while the desktop's NEW lasts as long as the app runs) and that no launch has reported yet. The human output is one line per report, `105  js  com.example.player  NEW  2 min ago  pid 7746 · 0.1.0 (1)  Error: …`, or `No crashes of your apps on <device>.`; device text (summary, version, build, device name) is shown with control characters as visible escapes, as `ovd logs` does, and `--json` keeps it as read. `--watch` prints that list, then polls the vault every 5 s (the next poll is scheduled after the previous finished) until Ctrl+C, which exits 0, and prints every report that appeared after the list as one more line, oldest first. With `--json` stdout is JSON lines: the list document, then one `{"ok": true, "crash": {…}}` per new report and, when the target goes offline (or disappears) and when it is back, an OVD line in the shape `ovd logs --json` uses, `{"time", "ovd": {"kind": "disconnected"}, "message"}` and `{"time", "ovd": {"kind": "reconnected"}, "message"}` (human: `HH:MM:SS.mmm OVD <name> went away · still watching for crashes` and `… is back · watching for crashes`). Polling goes on silently while the target is away, and what appeared meanwhile is announced once it is back. stderr gets `Watching <device> for crashes (Ctrl+C to stop)…` and each failed poll (an unreadable listing; the same error isn't repeated until a poll succeeds), in both modes; a failed poll doesn't end the command. A report of a package whose launch OVD is verifying (`ovd apps launch`, `ovd run`, any surface of this process) isn't announced until the verification ends, and then only if the launch didn't report it itself. Each announcement is one `crash.detected` activity entry (§4.4), which a log session shows as an OVD line. Exit codes: 0, 2 for an invalid id (see below), 3 without an SDK, 4 without an online target (before the list; `--watch` waits through an offline target once it has started), 1 for a listing the device refused or couldn't deliver (`COMMAND_FAILED`, with `--json` the `{"ok": false, "error": …}` document), 130 on a second Ctrl+C.

`ovd crash pull <id> [--out <path>] [--force]` (Stage 5.1) saves the whole crash report (`.acr`, about 350 KB, binary) of one crash from `ovd crashes` on the host. `<id>` is a non-negative integer of at most 9 digits without leading zeros, else `INVALID_CRASH_ID` (exit 2, before any SDK call); a report that isn't listed for the target, or isn't one of the developer's apps, is `CRASH_NOT_FOUND` (exit 1), so nothing out of scope is ever pulled. Without `--out` the file goes to the crashes folder, `OVD_CRASHES` if set (relative to the home folder), else `~/ovd/crashes`, created with mode 0700 on the first save (an existing folder keeps its mode) because a report holds the app's memory, named `<package>-<epoch>-<pid>.acr` with `-2`, `-3`… when that name is taken; the file is 0600. Like the captures folder (ADR 0022 Amendments), it holds the user's own files, not host state, so it is not under `OVD_HOME`. `--out` (relative to the working folder) is an existing folder, which gets the default name inside it, or a `.acr` file in an existing folder; anything else is `INVALID_PATH` (exit 2), a missing folder `PATH_NOT_FOUND` (exit 2), and an existing file `EXPORT_FILE_EXISTS` (exit 2) unless `--force` replaces it; all are checked before any SDK call. The save follows the rules of `ovd screenshot` below: private staging folder, no overwrite, no symlinked destination. On the device one script runs (`umask 077`, `mktemp -d /tmp/ovd-acr.XXXXXX`, `loggingctl vault --cat SYSTEM_TOMBSTONE <index>` into a file inside it, 30 s), then `vda pull` of that file (60 s), then always `rm -rf` of the folder, also after a failure or Ctrl+C. A report larger than 4 MB, a pull that fails or arrives with another size than the device reported, an empty file, something that isn't a report, or a script that fails, doesn't finish or answers unexpectedly is `CRASH_PULL_FAILED` (exit 1); the device's own refusal (status -7) is `CRASH_ACCESS_DENIED` (exit 1; the app may have been uninstalled since), and a report that left the vault meanwhile (-8) is `CRASH_NOT_FOUND`. An offline target exits 4. With `--json` it prints `{"ok": true, "crash": {…}, "path", "bytes"}` (`crash` as in `ovd crashes`, `path` absolute); the human line is `Saved /…/com.example.player-1762568340-7746.acr (301471 bytes): crash 105 of com.example.player`. Ctrl+C exits 1 (`Cancelled`, "Nothing was saved"). One `crash.pull` activity entry (§4.4).

`ovd reboot [--timeout <seconds>]` (Stage 4.5) reboots the target with `vega exec vda -s <serial> reboot` (15 s; it prints nothing and returns at once) and waits until the device is back. Not `vega device reboot`: its own wait ends at "connected", before `vega device info` answers (§8). Core polls the device every second, its info read fresh each time. First it must see the device away: not listed, listed `offline`, or listed without info. None of that within 30 s of answered polls is `REBOOT_FAILED` ("didn’t restart"; it may have restarted faster than a poll). Then the device must be online with info on every poll for 8 s, since VDA drops the Virtual Device once more after info first answers (§8); any other poll starts the 8 s again. A poll that fails (`VDA_UNAVAILABLE`, `COMMAND_FAILED`, `UNEXPECTED_OUTPUT`) counts as nothing; 10 in a row end the wait with that error. A Wi‑Fi stick VDA no longer lists (or OVD no longer knows) for 10 s gets one unlogged `vda connect` (5 s) every 10 s; one VDA still lists `offline` is left to VDA's own reconnect. The whole wait, settle included, has `--timeout` seconds, 120 by default, a whole number from 30 to 600 (else `INVALID_TIMEOUT`, exit 2, before any SDK call); past it, `REBOOT_TIMEOUT` (exit 1, "didn’t come back within 120 s", with `ovd vvd stop` / `ovd vvd start` as the Virtual Device's fix). Before the wait a target that isn't online exits 4, and `vda reboot` that fails is `TARGET_OFFLINE` for `not found` or `device offline` (exit 4), else `REBOOT_FAILED` (exit 1). After either answer core re-reads the device every second, up to 5 times, and sends `vda reboot` once more when it is listed online again (VDA's drop right after a start, §8); a device that doesn't come back in those polls, or a second `not found` or `device offline`, is `TARGET_OFFLINE`. stderr gets `Rebooting <name>…`, `Waiting for <name> to come back (up to 120 s)…` and, over Wi‑Fi, `Reconnecting <id> over Wi‑Fi…`; stdout `Rebooted <name> · back online in 16 s`. With `--json` it prints `{"ok": true, "reboot": {"target": {"id", "name"}, "seconds", "reconnected"}}`, where `reconnected` says OVD's own `vda connect` brought a Wi‑Fi stick back. Ctrl+C stops the wait and exits 1 (`Cancelled`, "The device may still be rebooting"). The desktop's Reboot & wait runs the same with the default timeout and echoes `ovd reboot --device <id>`. `OVD_REBOOT_SETTLE_MS` is a testing hook, as the `OVD_EMULATOR_*` overrides are: a whole number of milliseconds that replaces the 8 s settle (the e2e sandbox sets 500).

## 6. Desktop

- Electron + React + Vite (`electron-vite`), packaged with `electron-builder` (ADR 0004).
- **Main** runs core and exposes typed IPC handlers; batches high-volume data (logs) before IPC, and sends a reset of the log list (filter change, Clear, open) in bounded batches.
- **Preload** exposes one typed bridge; `contextIsolation` on, `nodeIntegration` off.
- **Renderer** is React UI: tokens, base components, screens.
- **Frame:** title bar (logo, version, target picker, Run ▸ with its steps dropdown, Watch toggle, palette search), sidebar (groups Device, Debug, Analyze, Automate, Setup), main area, status bar (SDK version, target, CLI echo with Copy). Watch shows only with a project folder open ("Watch off" / "Watching build/"); turning it on needs an online target and makes sure a log session follows it, and each new build reinstalls and relaunches through Run's steps, with a toast.
- **Design:** [OVD Desktop v2 in Claude Design](https://claude.ai/design/p/11662d93-ccfb-4d11-9761-b6fd499be3fd?file=OVD+Desktop+v2.dc.html). UI changes happen there first, then in code.
- **Screen view** (Remote & Screen, Stage 4.4), above the remote whatever its session's state. The Virtual Device: main opens emulator gRPC `streamScreenshot` (RGBA8888 at 960x540; gRPC turned on once when off) and sends one frame at a time over IPC as raw bytes, the next only after the renderer acked the last; core holds at most one frame more and stops reading the stream meanwhile, so HTTP/2 flow control holds the emulator back instead of frames piling up. The renderer draws each frame on a canvas ("Live · emulator gRPC"); while the window is hidden it draws and acks nothing, so the stream stays open and paused. When the stream ends, main reads the device up to 3 times 1 s apart: gone, offline or stopped shows "No signal"; still online (the Virtual Device restarted, or the stream dropped) reopens the stream once, unlogged, then shows the error with Retry. A booting Virtual Device shows "Waiting for …"; one that comes back online starts the view again. The stream closes when the screen unmounts, the window closes or reloads, and on quit. A stick has no live view: it shows its latest screenshot, "Latest screenshot · HH:MM:SS", with Refresh, which is `ovd screenshot --device <id>` (saved to the captures folder, logged, the Captures list refreshed, no clipboard); the header's Screenshot updates it too, and a key or text the device took after it marks it "Out of date". An offline target shows "No signal" above "Remote unavailable".
- **Reboot & wait** (Devices, Stage 4.5): a device's detail offers "Reboot & wait" while it is online (a stick or the Virtual Device), not while it is offline or stopped. While it runs, the button shows "Rebooting…" with a spinner, the device's status reads "Rebooting…" in the list, the detail, the target picker and the status bar, and a callout "Rebooting <name>… OVD waits until it’s back online." replaces the offline or stopped one; the device isn't offered as a target meanwhile. One reboot at a time per window. It ends with a toast, "<name> is back online · 16 s", or the error with Retry. Main closes the Remote's input session on that device first (a stick's console dies with the reboot) without telling the screen, opens none on it during the wait, and when the wait ends (back or failed) makes the screen open a new one. A live view of the device that went to "No signal" or an error opens its stream again once, unlogged; one still live stays as it is (qemu, its discovery file and emulator gRPC survive a guest reboot, §8). A log session needs nothing: its stream ends with the reboot and it reconnects as for any drop. Quitting stops the wait. A reboot from another surface (the CLI) gets no special handling: the stick's console that ended opens again on the next press (§4.1).
- **Crashes** (Debug → Crashes, Stage 5.1): the crash reports of the open target's developer apps, the same list as `ovd crashes` (echoed as `ovd crashes --device <id>`; the subtitle reads "loggingctl vault · scoped to your apps · polling every 5 s"). A table of reports (kind chip native or JS, app, NEW, age, summary, `pid · build · device`) and, once one is selected, a detail panel with its raw stack as plain text (never HTML or markdown, whatever the app wrote), and the actions Download ACR, Copy crash report path, Copy prompt for your agent, Logs at crash time (Logs, filtered to the app, at the crash's time) and, once the report is on disk, Show in folder (view-only, no echo). Download and the two copies echo `ovd crash pull <id> --device <id>` (ADR 0005); a copy pulls first when the report isn't downloaded yet, and two asks at once share one pull. The prompt is built in main by core's `agentPrompt`: a fixed text with OVD-validated values only (package, id, kind, pid, epoch, signal, the host path), then the device's text (version, build, reason, summary, stack) inside a fenced block labelled untrusted, capped at 200 lines of 500 characters, with fence characters and controls neutralised. Empty, loading, error (Retry) and no-target / offline-target states as the other screens. Main runs one crash watcher through core (`ovd.crashes.watch`, 5 s, following the selected target) while the window is visible and not minimized, on every screen, so the toast and the badge work everywhere; it starts and stops with the window, and core keeps the NEW baseline and the announced reports per device, so neither a repeat nor a miss follows. Each new report raises an error toast "<app> crashed · <summary>" with Open (shows it in Crashes), counts toward the badge on the sidebar's Crashes item, and is marked NEW until its detail is opened. Apps' "Crashed on launch" callout offers "Open crash report" when the launch has a `crash.id`. The renderer names a crash by `{device, id}` only, never a path: main keeps its own record of where each pull went, checks that the real path (links resolved) is an `.acr` inside the crashes folder before it copies or shows it, and puts the text on the clipboard itself. The desktop pulls into the crashes folder only (no `--out`).
- **Rules:** the design is the spec (ADR 0019); every action shows its CLI (ADR 0005); every screen has loading, empty, error and offline-target states; the sidebar grows with stages (ADR 0018); ⌘K / Ctrl+K palette; toasts (max 4, ~4 s).

## 8. Known SDK behavior

OVD designs around these. This list is the one home for SDK behavior: add new findings here, and the rules that follow from them to `docs/conventions/sdk.md`.

- A stick without Developer Mode is not listed by VDA at all (ADR 0009).
- Fire TV sticks are `armv7`; the Virtual Device matches the host, `x86_64` or `aarch64` (ADR 0008).
- `vega device install-app` installs a package built for another architecture without complaint (exit 0). Only the architecture guard stops it (ADR 0008).
- `vega device launch-app` reports success for apps that crash (ADR 0012). The recorded crashes came about 1 s after it returned; on the Virtual Device the crashing app never showed in `vlcm list`. OVD reads the crash history before the launch, watches `vlcm list --app-id` for 5 s, then reads the crash history again.
- A log session only sees apps installed before it started (ADR 0014): on a stick, a session started before the install showed none of the app's lines, filtered or not, through two installs and launches. A Release build of the pure-JS template (`developmentEnabled: false`) still sent its `console.log`, `info`, `warn` and `error` lines on the stick; a Debug build sends each one twice. `console.debug` never reaches the journal, and neither does any `console` call made before `AppRegistry.registerComponent`. On 2026-11-09, a throwaway app logging once at mount and every 3 s, Release and Debug, several launches each on a stick and on the Virtual Device: the JS lines came on every launch (the first after install, relaunches with the stream running or freshly started, the first after an uninstall and install, after an install over the app), so JS lines that stopped after the first launch (seen once on a stick on 2026-11-08) did not reproduce. A stream started before the app's first install showed none of the app's lines, only system lines about it; a stream started while the app was installed kept them across an uninstall and install, and across an install over it. A Debug build sent each line twice on the Virtual Device but once on the stick in this run, unlike the earlier stick recording; why is open. The root component's first-mount `console.log` and `console.warn` showed in only one launch.
- `loggingctl log` has no JSON mode, and with no option it prints its help and exits 2. `-o short_concise` (the default) prints `<Mon DD HH:MM:SS.ffffff> <host> <facility>.<priority> <identity>[<pid>]: <tid> <message>`; `short_precise` drops the priority and the tid. The time has no year and is the device clock, UTC on the stick. A multi-line message continues on lines with no header; journald's own lines have no tid. Priorities seen are `info`, `warning` and `err`; no `debug` lines are kept. An app's lines carry its full package ID as identity (checked up to 33 characters); some native system processes show only its last 15 characters (`thouse.launcher`). The tag is part of the message (`<tid> I SmartBox:…`, `<tid> INFO com.amazon.keplerscript: …`), and `-a` matches it.
- `loggingctl log -f` first prints what the journal still holds (30–60 s on a stick), then follows. A stream started right after another was stopped prints the stopped one's last lines again, byte for byte: 573 lines (about 12 s) on the Virtual Device, as in `fixtures/0.24/loggingctl-log/virtual-device-restart-before.txt` and `virtual-device-restart-after.txt`, and 303 lines on a stick; core drops what it already delivered. `-v <package>` keeps the lines whose identity is that package, with their continuation lines; `-p <priority>` keeps exactly that priority (repeat it for several); `-S` and `-U` accept only `HH:MM:SS`. An unknown priority and every other time format are silently ignored (exit 0, nothing filtered).
- The device drops an app's lines above 300 per second per tag and says so in the stream (`Process exceeds log limit of [300] lps for tag […]`, later `Last log suppression ended for tag […]. [N] logs suppressed`). Lines reach the host about 0.2 s after their timestamp.
- `vega exec vda shell …` runs as a chain of about seven host processes (`vega`, bash, python, node, python, bash, then the native `vda`). SIGTERM to the top `vega` leaves the rest, and the device's `loggingctl`, running; a process started in the background of a non-interactive shell ignores SIGINT. SIGTERM to the whole process group, or to the native `vda`, ends every host process and the device's `loggingctl`. When the device drops (a reboot), a `loggingctl log -f` stream ends by itself with exit 0 and nothing on stderr.
- On the Virtual Device, `inputd-cli` key presses report success but don't reach apps, and `gwsi-tool-screenshooter` fails. Emulator gRPC works: `sendKey` (OK = `kpenter`, Back = `KEY_BACK`, Home can't be sent) and `getScreenshot` (ADR 0010).
- The emulator gRPC endpoint is off after every Virtual Device start. It is enabled through the emulator console (`grpc <port>`) with the token from `~/.emulator_console_auth_token`.
- The emulator console (SDK 0.24.12112, macOS aarch64, checked 2026-11-11) listens on 127.0.0.1 at the port in VDA's serial (`emulator-5554` → 5554). It greets with `Android Console: Authentication required` lines and a bare `OK`, in CRLF lines and several chunks; a reply is complete only at a line that is exactly `OK` or starts with `KO`. Any command before `auth <token>` answers `KO: unknown command, try 'help'`, a wrong token `KO: authentication token does not match ~/.emulator_console_auth_token`. `grpc 8554` answers `OK: { "port": "8554" }`, `OK: gRPC endpoint available at port 8554` and `OK`, and can be repeated (`fixtures/0.24/emulator-console`).
- Only after `grpc <port>` does the emulator write its discovery file, `~/Library/Caches/TemporaryItems/avd/running/pid_<qemu pid>.ini` on macOS (`key=value`: `port.serial`, `grpc.port`, `grpc.token`, an 88-character base64 token, and more; `fixtures/0.24/emulator-discovery`). A crashed emulator leaves its file behind, so OVD checks that the pid is alive. The Linux folders (`$XDG_RUNTIME_DIR/avd/running`, `/run/user/<uid>/avd/running`, `~/.android/avd/running`) are unverified.
- Emulator gRPC is h2c and needs `authorization: Bearer <grpc.token>`: without it every call answers HTTP 200 with `grpc-status: 16` in the headers. `sendKey` (`KeyboardEvent`, `codeType` 1 Evdev, `eventType` 0 down or 1 up, `keyCode`) answers status 0 with an empty message, `getVmState` status 0 with `08 01` (RUNNING) (`fixtures/0.24/emulator-grpc`).
- `inputd-cli start` (SDK 0.24.12112, checked on the Virtual Device on 2026-11-11) is a console on stdin: it greets with `Welcome to the Inputd command line!` and `Type 'h' …`, then the prompt `inputd-cli > `, ready about 1.1 s after start; each reply is its lines, then `\n\r\n`, then the next prompt. `button_press <KEY_…>` answers `Injecting Button Press As Driver: <KEY_…> State: short` in about 0.3 s; every evdev name tried was accepted (`KEY_UP`, `DOWN`, `LEFT`, `RIGHT`, `ENTER`, `SELECT`, `BACK`, `HOMEPAGE`, `MENU`, `PLAYPAUSE`, `REWIND`, `FASTFORWARD`), and an unknown one answers `invalid button value: [KEY_NOPE]`. The one-shot form (`inputd-cli button_press KEY_NOPE`) exits 0 for an invalid key too, so only the reply tells success. `send_text` in the console splits on spaces: the text must be in double quotes, with `\"` and `\\` as escapes inside, and UTF-8 passes through (about 0.1 s per character); unquoted words answer the argument count and `send_text provided with an invalid number of arguments.` `exit` prints `exiting...` and exits 0 (`fixtures/0.24/inputd-cli-console`). Whether these key names reach apps on a stick, and what a second console on the same stick (another surface) does, are unverified (#43); OVD treats any reply but the success line, and an early exit, as `INPUT_FAILED`.
- Emulator gRPC `sendKey` with evdev key codes, a key down then up, reaches apps on the Virtual Device (focus moved in the launcher and in the template app; 2026-11-11). The `KeyboardEvent.text` field (`eventType` keypress) typed `hello` but dropped or garbled text with capitals (`ABC` became `A'BC`, with shift left stuck), while one evdev key per character, wrapped in an explicit `KEY_LEFTSHIFT` (42) down and up where needed, typed `Hello World! A-1 "q"?` exactly. OVD types on the Virtual Device that way, refuses characters outside printable ASCII before sending anything, sends a whole press or text over one h2c session, and sends a shift up after a sequence with a shift down that failed.
- Emulator gRPC `getScreenshot` with an empty `ImageFormat` (SDK 0.24.12112, Virtual Device aarch64, checked 2026-11-12) answers HTTP 200 with `grpc-status: 0` in the trailers, about 940 KB in 345 ms: an `Image` message with `format` (field 1: rotation, width 1920, height 1080), the PNG itself (field 4, 1920x1080 RGBA) and `timestampUs` (field 6) (`fixtures/0.24/emulator-grpc/get-screenshot.json`, its image replaced with a synthetic PNG).
- `gwsi-tool-screenshooter <file>.png` on the Virtual Device hung (stopped after 30 s) and left an empty file; nothing was left running on the device or the host. `-h`, or a name that doesn't end in `.png`, prints its usage on stderr and exits 1 (`fixtures/0.24/gwsi-tool-screenshooter`). Not yet checked on a stick (#44): OVD gives it 15 s, during which the serial runner holds every other SDK call. The device's `/tmp` is writable by the shell user.
- `vda pull <remote> <local>` prints `<remote>: 1 file pulled, 0 skipped. …` and exits 0; a remote that doesn't exist prints `vda: error: failed to stat remote object '<remote>': No such file or directory` on **stdout** and exits 1; an empty remote pulls an empty file with exit 0 (`fixtures/0.24/vda-pull`). The fake SDK's stick screenshot (exit 0, no output, then the synthetic PNG through `pull`) is synthesized from these, not recorded on a stick (#44).
- Emulator gRPC `getScreenshot` sizes and formats (SDK 0.24.12112, macOS aarch64, 8 calls each, checked 2026-11-12): PNG at the native 1920x1080 took 324 ms (3.1 fps), PNG 960x540 120 ms (8.3 fps), PNG 640x360 56 ms (17.8 fps), RGBA8888 960x540 5.5 ms (about 2 MB) and RGB888 960x540 5.8 ms. ## 9. Testing

- Vitest in every package; tests mirror `src/` under each package's `test/`.
- No hardware, SDK, network or real timers in tests. Core uses a fake runner that replays fixtures from `fixtures/<sdk-version>/`.
- Fixtures are sanitized with the neutral sample data (ADR 0016).
- CLI tests assert `--json` output and exit codes. No snapshot tests.
- End-to-end tests (`e2e/`, `pnpm run test:e2e`) run the built CLI and desktop app against a fake SDK that answers only with recorded fixtures (ADR 0023). They check user flows, the SDK commands run and the state left behind. CI runs them as the required `e2e` job.
- Real-device behavior is checked manually. The nightly SDK check (Stage 3.7, ADR 0007) covers the Virtual Device: `.github/workflows/nightly-sdk-check.yml` installs the latest SDK on `ubuntu-latest` and runs `scripts/nightly-sdk-check.mjs`. The script starts a headless Virtual Device, builds a throwaway `com.example.hellovega`, and runs `doctor`, `devices`, `pkg info`, `install`, `apps launch` and `logs` from the built CLI with `--json`. A recording `vega` shim at `OVD_VEGA` (core checks it before PATH) records every SDK call. The output is sanitized and leak-checked, and laid out as fixtures when the SDK's major.minor has no folder yet. A failed scheduled run opens or comments on the issue "Nightly SDK check failed".
