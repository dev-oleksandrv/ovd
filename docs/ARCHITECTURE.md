# Architecture

## 1. Overview

OVD (Open Vega DevTools) is an open-source, editor-agnostic toolkit for Vega OS devices. Its goal: the fastest way to go from "I have a .vpkg" to "I see it running and I know what it's doing", on any Vega device, from any terminal, editor, CI job or AI agent.

The official Vega tooling can do everything, but it is spread across about ten CLIs and two shells (host and device), prints raw text, and its friendly layer lives only inside VS Code. OVD wraps those tools behind one consistent, scriptable interface.

**Users:**

| User                                      | Main job                                           | Priority  |
| ----------------------------------------- | -------------------------------------------------- | --------- |
| Indie or small-team Vega developer        | Build → install → see logs → fix, many times a day | Primary   |
| Developer porting a Fire OS (Android) app | Find adb / Logcat / scrcpy equivalents             | Secondary |
| QA engineer with a Fire TV stick          | Install a build, drive the app, capture evidence   | Secondary |
| CI pipeline                               | Automated smoke tests on every commit              | Later     |
| AI coding agent                           | Install, launch, read logs, look at the screen     | Later     |

**Constraints:**

- **Open source** (Apache-2.0), public from day one: no secrets or personal data in the repo (ADR 0015).
- **Wrap, don't reimplement:** the user's installed Vega SDK does the work; OVD never bundles it (ADR 0002).
- **Platforms:** macOS and Ubuntu only (ADR 0013).
- **Scriptable:** `--json` on every command (ADR 0006).
- **Testable without hardware:** recorded SDK outputs are the fixtures (ADR 0007).

**Non-goals:** replacing Vega Studio, the build system or the React Native debugger; Windows support while the SDK lacks it; redistributing SDK binaries; reimplementing device protocols; duplicating Amazon Builder Tools' docs search and trace analysis.

## 3. Dependency rules

- Dependencies flow `apps/* → packages/core`. Core never imports from `apps/`; surfaces never import each other.
- Surfaces import `@ovd/core` through its entry, never deep paths.
- Only core runs SDK tools and parses their output.
- The desktop and the MCP server call core in-process; nothing shells out to `ovd` (ADR 0001).
- The renderer never imports core runtime code and never gets Node APIs; it talks to main through the preload bridge (ADR 0004).

## 4. Core

### 4.1 SDK runner

- Discovers the Vega CLI (SDK Manager) and the active SDK version: `OVD_VEGA`, then every `vega` on `PATH`, then `~/vega/bin/vega` (a desktop app doesn't inherit the shell `PATH`). The manager wins over a `vega` bundled inside an SDK, which lacks `vega sdk` and `vega devmode`. Device commands fail with an install hint when none is found.
- Every call goes through one runner: target injection (`--device <id>` for `vega device …`, `-s <serial>` for `vega exec vda …`), timeout, `AbortSignal`, captured stdout/stderr/exit code.
- VDA runs as `vega exec vda …`. Device tools run through `vega exec vda shell` (`shell -c <component>` for component scope).
- Long-running processes are managed: explicit start and stop, reconnect when a device drops, no orphans. The log stream (`loggingctl log -f`) is built: it runs in its own process group and is stopped by signalling the group. A stream that ends by itself has what is left of its group stopped (SIGTERM, then SIGKILL) before the runner unregisters it. A log session reconnects when its stream ends by itself: it reads the target every 2 s and starts a new stream once the target is back, and gives up (`LOG_STREAM_ENDED`) after 5 minutes away or three streams in a row that end at once. It also restarts the stream after every install OVD makes on the target (ADR 0014), and drops the journal backlog a new stream prints again (§8). Probes stopped by `stopWhen` (the `vega devmode login --json` sign-in probe) run in their own process group too, and are stopped as a group on a match, a timeout or an abort. Planned: the input console (Stage 4) and memory polling (Stage 6). Core keeps a process-wide registry of the live detached groups (`packages/core/src/sdk/processGroups.ts`), so none outlives OVD: the CLI SIGTERMs every registered group on exit, a second Ctrl+C, SIGTERM or an uncaught error, and the desktop aborts its running probes and the stream on `before-quit` and SIGTERMs what is left on `will-quit`. A SIGKILL of OVD or a hard crash (native crash, OOM kill) runs nothing, so those groups stay.

### 4.2 Adapters

- JSON modes first: `vega device info` (JSON by default, no `--json` flag), `vega sdk … --json`, `vega devmode … --json`, `vpt info --json`, `loggingctl vault --json-dump`.
- Text parsers stay small. Output is validated with `zod`. A changed format gets a new versioned adapter (ADR 0007).

### 4.3 Target

- The target is one device ID (USB serial, `IP:port` over Wi‑Fi, or the Virtual Device). It is remembered between launches. `VEGA_SERIAL` and `--device` override it.
- Paired Wi‑Fi devices are remembered and listed as `offline` while unreachable.

### 4.4 Activity log

Every device action is appended to a host-side, append-only log: time, surface, action, target, arguments, result. The desktop's Logs timeline and "Recent agent calls" read it (ADR 0011). Failures before the target is known (no app, no target, an offline target, an invalid app ID) are logged too, with `target: null`. Core tails `activity.jsonl` (the activity feed, every 500 ms), so a log session sees the installs and launches of every OVD process: it shows them as OVD lines and restarts its stream after an install, across surfaces. A log session's restarts are logged as `logs.restart` with `reason` `install` or `reconnect`; a reconnect that gives up is a `logs.restart` error with `LOG_STREAM_ENDED`. A watch (`ovd run --watch`, the desktop's Watch) logs each settled batch of its build folder as `build.changed`, with `folder` (`build/<arch>-<type>/`), `file` and `redeploy` (whether a build fit the target); its target is the target device even when it is offline (then an error with `TARGET_OFFLINE`), and null only without a target.

### 4.5 Errors

Core returns typed errors: a stable `code`, a `message` and a one-line `hint`. Surfaces format them.

## 5. CLI

- Thin `commander` layer. Human output by default; `--json` everywhere (ADR 0006).
- JSON mode: one document on stdout (JSON lines for streams), everything else on stderr. Errors: `{"ok": false, "error": {"code", "message", "hint"}}`.
- Streams stop cleanly on Ctrl+C.

**Exit codes:**

| Code | Meaning                                                                                                            |
| ---- | ------------------------------------------------------------------------------------------------------------------ |
| 0    | Success                                                                                                            |
| 1    | Failure (generic)                                                                                                  |
| 2    | Usage error                                                                                                        |
| 3    | SDK missing or unusable                                                                                            |
| 4    | Device not found, target offline or no target                                                                      |
| 5    | External step not completed (not signed in, code rejected, pairing failed)                                         |
| 6    | Architecture mismatch: the package doesn't match the target (ADR 0008)                                             |
| 7    | Launch not verified: the app crashed or isn't running after launch                                                 |
| 129  | Stopped because the terminal was closed (SIGHUP; the shell's code)                                                 |
| 130  | Stopped at once by Ctrl+C (a second Ctrl+C, or Ctrl+C on a command that can't cancel; the shell's code for SIGINT) |
| 143  | Stopped by SIGTERM (the shell's code)                                                                              |

The app commands exit 1 for an app that isn't installed (`APP_NOT_INSTALLED`) or isn't side-loaded (`NOT_SIDELOADED`) and for an install, launch, terminate or uninstall the SDK refuses (`INSTALL_FAILED`, `LAUNCH_FAILED`, `TERMINATE_FAILED`, `UNINSTALL_FAILED`), which scripts tell apart by `error.code` in `--json`, and exit 2 for an invalid app ID (`INVALID_APP_ID`) or no app given with nothing open (`NO_APP`). `ovd apps launch` and `ovd apps restart` exit 7 (`LAUNCH_NOT_VERIFIED`) for both `"reason": "crashed"` and `"reason": "not-running"`. `ovd apps launch` on an app that already runs does nothing and exits 0 with `"wasRunning": true` and `"launched": false`.

`ovd logs` restarts the stream after every install OVD makes on the target (`--no-restart-after-install` keeps it running) and reconnects when the device drops. It exits 0 on Ctrl+C and when `--until` is reached, 1 only when reconnecting gives up (`LOG_STREAM_ENDED`: the device stayed away 5 minutes, or three streams in a row ended at once), 2 for an invalid filter (`INVALID_LOG_FILTER`, `INVALID_APP_ID`, `--app` with `--system`), 3 without an SDK and 4 without an online target; with `--json` it prints one JSON object per entry (`time`, `level`, `priority`, `facility`, `process`, `pid`, `tid`, `tag`, `message`, `parsed`) and ends a failed stream with the `{"ok": false, "error": …}` line. The human output shows control characters in device text (tag and message, all but tab and newline) as visible escapes, `\x1b` or `\u{202e}`, so a log line can't move the cursor, recolor or reorder the terminal; `--json` keeps the device text exact. OVD's own events (installs, launches, crashes, restarts, disconnects, reconnects, and a watched build folder's new build, `Build folder changed: build/aarch64-debug/player_aarch64.vpkg`) print inline as OVD lines: `HH:MM:SS.mmm OVD <message>`, and with `--json` `{"time", "ovd", "message"}`, where `ovd` is the event with its `kind`.

`ovd logs --export <file>` writes the lines to the file instead of stdout and follows as `ovd logs` does (Ctrl+C, `--until` or a stream that gives up end it). `--format text` (the default) is the human line format, control characters escaped; `--format jsonl` is one `--json` line per entry, device text exact. An existing file is refused (`EXPORT_FILE_EXISTS`, exit 2) unless `--force`; a file or folder that can't be written is `EXPORT_FAILED` (exit 1). Both are checked before the stream starts, and the file is only opened (an existing `--force` target only replaced) once there are lines to write or the run ends normally, so a start that fails leaves no file. On stop it prints `Exported N lines to <file>`, or with `--json` one document `{"ok": true, "path", "format", "lines"}` (`path` absolute); a stream that gives up still closes the file and ends with the `{"ok": false, "error": …}` document, exit 1. `--format` or `--force` without `--export` is a usage error (exit 2). The desktop's Export (plain text or JSON lines) writes the same formats and echoes `ovd logs … --until <last exported line> --export <file> [--format jsonl] [--force] --device <id>`.

`ovd run [app] [--force]` is the one-click deploy (Stage 3.4). Without `app` it takes the open project or .vpkg, like `ovd apps install`. From a project folder it picks the build that matches the target's architecture (from `vega device info`, ADR 0008), preferring a Debug build (`build/<arch>-debug/`) on the Virtual Device and a Release build (`build/<arch>-release/`) on a stick, and the newest matching build when there is none of that type. It installs it behind the architecture guard, starts the log session, then restarts the app (a graceful stop if it still runs, then `launch-app`), so every run ends with a fresh launch of what it installed, verified against `vlcm list` and the crash history (ADR 0012). Then it follows the log as `ovd logs` does. Progress goes to stderr (`Found build build/aarch64-debug/player_aarch64.vpkg (debug)`, `Installing on …`, `Starting the log session…`, `Launching…`, `Verifying launch…`); stdout gets the install and launch lines, then the log lines. With `--json` stdout is JSON lines: first `{"ok": true, "run": {"target", "package", "forced", "launch"}}` (`package` is the install's, with `buildType` and, for a project build, `folder`; `launch` is the `ovd apps restart` result), then the `ovd logs --json` lines. Log lines that arrive before the launch is verified are held and printed after the run document, so it is always the first line. A run writes no activity entry of its own: the install (`app.install`), the session (`logs`) and the launch (`app.restart`) write theirs. Exit codes: 0 on Ctrl+C while following, 1 when the stream gives up (`LOG_STREAM_ENDED`, its `{"ok": false, "error": …}` line last), 2 with nothing to run (`NO_PACKAGE`), 4 without an online target (`TARGET_OFFLINE`, `NO_TARGET`; nothing is installed), 6 on an architecture mismatch without `--force` (nothing is installed), and 7 when the launch isn't verified: one `{"ok": false, "error": {"code": "LAUNCH_NOT_VERIFIED", …}, "run": …}` document with the crash in `run.launch.crash`, the held log lines dropped and the session stopped. Ctrl+C before the launch is verified stops the run after the step in flight (no launch after it), stops the session if it started, and exits 0 with nothing on stdout, as `ovd logs` stopped before its first line does. The desktop's Run ▸ runs the same with no ref (a dropped .vpkg is opened first) and echoes `ovd run --device <id>`.

`ovd run --watch [app]` (Stage 3.5) redeploys every new build of a project folder: `app` must be a Vega project folder, or the open project is one; a .vpkg, a package ID or nothing open is `NOT_A_PROJECT` (exit 2, before any SDK call). It watches `build/` on the host by polling it every second with `stat` (not `fs.watch`, §8): what is there when it starts is the baseline, a new or changed package counts once its size and mtime held for one poll, and the packages that settle together are one batch, so a build of every architecture is one redeploy, about 2 s after the last package is written. It starts the watch, then runs once as `ovd run` does, then, for each batch, reads the target fresh and picks the changed build that fits it (its architecture, the target's build type first, then the newest). It prints `Watching build/ for new builds (Ctrl+C to stop)…`, and per batch `Build changed: build/aarch64-debug/player_aarch64.vpkg, redeploying…`, `… no build for <target>`, or the target's error, on stderr, and redeploys with `ovd run <that .vpkg> --device <target>`. Runs go one at a time: a batch that settles during a run is redeployed after it. No run result ends the command: every run, the first and each redeploy, prints its document (`{"ok": true, "run": …}`, or `{"ok": false, "error": …}` with `"run"` for an unverified launch) or human lines, and the log session keeps running through failed runs. A redeploy's install restarts that session (ADR 0014), and the redeploy launches once it restarted (or after 15 s); a session is started only when none runs (the first run failed before its log step). Each batch writes one `build.changed` activity entry, which the session shows as an OVD line; while no session runs, the stderr line is the only trace. Held log lines apply to the first run only. Exit codes: 0 on Ctrl+C, 1 when the stream gives up (`LOG_STREAM_ENDED`, its error document last), 2 when it isn't a project, 130 on a second Ctrl+C. The several run documents and the `ok: false` that doesn't end the stream are `--watch` only; plain `ovd run` is unchanged. The desktop's Watch toggle watches the open project for the target and echoes `ovd run --watch --device <id>`; it turns off when another project is opened (from any surface).

## 6. Desktop

- Electron + React + Vite (`electron-vite`), packaged with `electron-builder` (ADR 0004).
- **Main** runs core and exposes typed IPC handlers; batches high-volume data (logs) before IPC, and sends a reset of the log list (filter change, Clear, open) in bounded batches.
- **Preload** exposes one typed bridge; `contextIsolation` on, `nodeIntegration` off.
- **Renderer** is React UI: tokens, base components, screens.
- **Frame:** title bar (logo, version, target picker, Run ▸ with its steps dropdown, Watch toggle, palette search), sidebar (groups Device, Debug, Analyze, Automate, Setup), main area, status bar (SDK version, target, CLI echo with Copy). Watch shows only with a project folder open ("Watch off" / "Watching build/"); turning it on needs an online target and makes sure a log session follows it, and each new build reinstalls and relaunches through Run's steps, with a toast.
- **Design:** [OVD Desktop v2 in Claude Design](https://claude.ai/design/p/11662d93-ccfb-4d11-9761-b6fd499be3fd?file=OVD+Desktop+v2.dc.html). UI changes happen there first, then in code.
- **Rules:** the design is the spec (ADR 0019); every action shows its CLI (ADR 0005); every screen has loading, empty, error and offline-target states; the sidebar grows with stages (ADR 0018); ⌘K / Ctrl+K palette; toasts (max 4, ~4 s).

## 8. Known SDK behavior

OVD designs around these. This list is the one home for SDK behavior: add new findings here, and the rules that follow from them to `docs/conventions/sdk.md`.

- A stick without Developer Mode is not listed by VDA at all (ADR 0009).
- Fire TV sticks are `armv7`; the Virtual Device matches the host, `x86_64` or `aarch64` (ADR 0008).
- `vega device install-app` installs a package built for another architecture without complaint (exit 0). Only the architecture guard stops it (ADR 0008).
- `vega device launch-app` reports success for apps that crash (ADR 0012). The recorded crashes came about 1 s after it returned; on the Virtual Device the crashing app never showed in `vlcm list`. OVD reads the crash history before the launch, watches `vlcm list --app-id` for 5 s, then reads the crash history again.
- A log session only sees apps installed before it started (ADR 0014): on a stick, a session started before the install showed none of the app's lines, filtered or not, through two installs and launches. A Release build of the pure-JS template (`developmentEnabled: false`) still sent its `console.log`, `info`, `warn` and `error` lines on the stick; a Debug build sends each one twice. `console.debug` never reaches the journal, and neither does any `console` call made before `AppRegistry.registerComponent`. On 2026-11-09, a throwaway app logging once at mount and every 3 s, Release and Debug, several launches each on a stick and on the Virtual Device: the JS lines came on every launch (the first after install, relaunches with the stream running or freshly started, the first after an uninstall and install, after an install over the app), so JS lines that stopped after the first launch (seen once on a stick on 2026-11-08) did not reproduce. A stream started before the app's first install showed none of the app's lines, only system lines about it; a stream started while the app was installed kept them across an uninstall and install, and across an install over it. A Debug build sent each line twice on the Virtual Device but once on the stick in this run, unlike the earlier stick recording; why is open. The root component's first-mount `console.log` and `console.warn` showed in only one launch.
- `loggingctl log` has no JSON mode, and with no option it prints its help and exits 2. `-o short_concise` (the default) prints `<Mon DD HH:MM:SS.ffffff> <host> <facility>.<priority> <identity>[<pid>]: <tid> <message>`; `short_precise` drops the priority and the tid. The time has no year and is the device clock, UTC on the stick. A multi-line message continues on lines with no header; journald's own lines have no tid. Priorities seen are `info`, `warning` and `err`; no `debug` lines are kept. An app's lines carry its full package ID as identity (checked up to 33 characters); some native system processes show only its last 15 characters (`thouse.launcher`). The tag is part of the message (`<tid> I SmartBox:…`, `<tid> INFO com.amazon.keplerscript: …`), and `-a` matches it.
- `loggingctl log -f` first prints what the journal still holds (30–60 s on a stick), then follows. A stream started right after another was stopped prints the stopped one's last lines again, byte for byte: 573 lines (about 12 s) on the Virtual Device, as in `fixtures/0.24/loggingctl-log/virtual-device-restart-before.txt` and `virtual-device-restart-after.txt`, and 303 lines on a stick; core drops what it already delivered. `-v <package>` keeps the lines whose identity is that package, with their continuation lines; `-p <priority>` keeps exactly that priority (repeat it for several); `-S` and `-U` accept only `HH:MM:SS`. An unknown priority and every other time format are silently ignored (exit 0, nothing filtered).
- The device drops an app's lines above 300 per second per tag and says so in the stream (`Process exceeds log limit of [300] lps for tag […]`, later `Last log suppression ended for tag […]. [N] logs suppressed`). Lines reach the host about 0.2 s after their timestamp.
- `vega exec vda shell …` runs as a chain of about seven host processes (`vega`, bash, python, node, python, bash, then the native `vda`). SIGTERM to the top `vega` leaves the rest, and the device's `loggingctl`, running; a process started in the background of a non-interactive shell ignores SIGINT. SIGTERM to the whole process group, or to the native `vda`, ends every host process and the device's `loggingctl`. When the device drops (a reboot), a `loggingctl log -f` stream ends by itself with exit 0 and nothing on stderr.
- On the Virtual Device, `inputd-cli` key presses report success but don't reach apps, and `gwsi-tool-screenshooter` fails. Emulator gRPC works: `sendKey` (OK = `kpenter`, Back = `KEY_BACK`, Home can't be sent) and `getScreenshot` (ADR 0010).
- The emulator gRPC endpoint is off after every Virtual Device start. It is enabled through the emulator console (`grpc <port>`) with the token from `~/.emulator_console_auth_token`.
- `vega device info` reports no uptime or storage. `vlcm` lifespan is a state, not a duration.
- Crash and log access is scoped to the user's own app.
- Metro runs on the host; its output isn't in the device log stream.
- The KPI Visualizer fails warm starts on the Virtual Device and fails offline apps.
- `vpt` isn't on PATH; it runs as `vega exec vpt …`. Two `vpt` calls at once crash the SDK wrapper.
- `react-native build-vega --build-type Release|Debug` (the `helloWorld` template, SDK 0.24.12112, checked 2026-11-10) writes a package for every architecture of that type, `build/<armv7|aarch64|x86_64>-<release|debug>/<name>_<arch>.vpkg`, plus copies in its `private` folder, which OVD skips. Debug and Release packages share the file name: only the folder, and `developmentEnabled` in the app config (`true` in Debug), tell them apart, and the folder always matched the config. Each `vpt` call takes about 0.35 s. `vega run-app <vpkg> <component> -d <serial>` installs and launches in about 1.7 s on the Virtual Device, with no launch verification; OVD's run installs and restarts through the same calls as `ovd apps install` and `ovd apps restart` instead.
- `react-native build-vega` (the `helloWorld` template, SDK 0.24.12112, checked on the Virtual Device on 2026-11-10) packs each architecture in turn into `build/private/kepler/…/<arch>/<Type>/…vpkg`, then copies it to `build/<arch>-<type>/<name>_<arch>.vpkg` and writes `vpkg-info.json` next to it, in the order aarch64, armv7, x86_64: about 0.5 s apart for a 1 MB package, 6 s for an 80 MB one. The copy is written in place (the same inode on a rebuild, a new one after a clean build) and incrementally: an 80 MB copy shows partial sizes for about 50 ms, and the first `fs.watch` event fires on the partial file. macOS FSEvents coalesce: a 5 s pack of the private file gave 2 events. `npm run clean` deletes `build/`. OVD's watch therefore polls with `stat` and takes a package once its size and mtime held for one poll.
- `vpt info --json` reports no architecture and no build type, and its `size` is the unpacked contents without `meta-info/`, not the file's size. The build type is `developmentEnabled` in `assets/raw/keplerscript-app-config.json` (`vpt dump`). `vpt checksum` prints SHA-384.
- GitHub's arm64 macOS runners can't start the Virtual Device (ADR 0013).
- Two CLIs answer to `vega`: the Vega CLI (SDK Manager, `~/vega/bin/vega`) and the one bundled inside each SDK. The bundled one has no `sdk` or `devmode`: `vega devmode login --json` there exits 253 with `Unknown arguments`.
- `vega devmode login --json` is the only sign-in probe: signed in, it exits 2 at once ("Already logged in"); signed out, it prints `"status": "pending"` with a verification URL and code, opens no browser, and waits. Doctor stops it at `pending`. Once the browser sign-in finishes, it prints `"status": "success"` and exits 0.
- `vega devmode enable-device --code <code> --json` answers in 1–4 s: exit 0 `success`, exit 2 when signed out, exit 6 "Invalid code" for a wrong, malformed or already-used code. The code on the TV is 6 letters and digits with no dash. On success the stick leaves the VDA list at once, reboots and is back on USB about 40 s later; `vega device info` prints empty fields for a moment after that. Code expiry, and what several vendors do without a terminal, are not verified yet.
- `vega device info` exits 0 with empty fields for an unknown or still-booting device, or when several devices are connected and no `--device` is given.
- The Virtual Device is `VirtualDevice` to `vega device` and `emulator-5554` to VDA.
- `vega virtual-device start` blocks until "Virtual device ready." (about 6 s) and VDA lists the device right after. On a running Virtual Device it exits 0 anyway ("Failed to launch: virtual device is already running" on stderr), so OVD checks the status first. `stop` on a stopped one exits 1 ("virtual device not running").
- Virtual Device Developer Mode survives a restart. Right after `vsm developer-mode disable` the device shell stops answering (`No running instances of com.amazon.dev.shell.service`) and `vega device info` prints empty fields until the Virtual Device restarts. `inDeveloperMode` in `vega device info` follows `vsm developer-mode`.
- `vda tcpip <port>` removes the stick's USB entry from the VDA list at once, and it stays gone, across power cycles, until `vda usb`. A stick in TCP/IP mode is only listed after `vda connect`; the host doesn't even see it as a USB device. It switches back with `vda -s <ip:port> usb` (so only while connected) or on the TV in Developer Options → Connection Mode → USB; `ovd forget` runs `vda usb` for a stick it switched itself. OVD reads the stick's IP over USB (`/proc/net/fib_trie`; the stick has no `ip`, `ifconfig` or `getprop`) before switching.
- `vda connect` exits 0 whatever happens; only stdout tells success (`connected to`, `already connected to`) from `Connection refused`, `Operation timed out` (after 47–75 s) or a bad address. OVD stops it after 20 s.
- Over Wi‑Fi no command returns the serial: `vda get-serialno` prints the `IP:port`, `/proc/idme` is permission denied, and `vega device info` matches USB except `deviceName`. A stick paired over USB keeps the serial OVD read before switching; one paired by IP has none.
- A Wi‑Fi device that drops stays in the VDA list as `offline`, and VDA reconnects it by itself when it comes back. After a host or VDA server restart it is gone from the list until `vda connect`.
- No command reports a friendly device name; `deviceName` echoes the ID passed in.
- `vega device list` takes 1–4 s and has no JSON mode; `vega exec vda devices -l` takes about 0.3 s.
- A Vega project records no SDK version. It pins an OS version (`manifest.toml` → `[os.version] target`) and a React Native version (`package.json`); `vega sdk use` sets the SDK for the whole machine.
- `vega project doctor` has no JSON mode. It checks the folder it runs in (OVD sets the working directory), prints one `✅`/`⚠️`/`❌` line per check and "To fix" bullets, takes about 2 s, works before `npm install`, and never changes the project. It exits 1 when any check fails and 0 otherwise (warnings alone exit 0); outside a project it fails one "Project config" check.
- `vega platform doctor` prints the whole environment, secrets included. OVD never runs it.
- Two `vega` processes started at the same moment can break each other: the SDK relinks its workspace and rewrites a cache on every start, and the loser fails with `[Errno 2] No such file or directory: 'vda'` (exit 2) or `EOFError`. Each core runs one SDK command at a time, and retries the device list once for clashes with another surface. Reaching the same SDK by two paths makes it worse: the Vega CLI runs it as `~/vega/sdk/vega-sdk/main/<version>` (a symlink), the SDK's own `~/vega/sdk/<version>/bin/vega` as `~/vega/sdk/<version>`, and every call on the other path than the last one deletes and rebuilds `~/vega/sdk/<version>/workspace/env` (`~/vega/sdk/<version>/tools/bin/config.py`). With the desktop polling through the Vega CLI, terminal builds through the SDK's `bin` failed every time (issue #30).
- `vega exec vda shell <command>` re-wraps the command in a host `sh -c "…"`: `$`, quotes and parentheses in it are expanded or broken on the host. Pipes survive. OVD sends single commands with plain arguments, and a script that needs more as `echo <base64> | base64 -d | sh` (the device has `base64`, `mktemp` and Toybox `xargs` with `-P` but no `-I`).
- `vda -s <id> shell …` for an ID VDA doesn't list prints `vda: device '<id>' not found` on stderr and exits 1, whatever the command.
- No app command has a JSON mode. `vega device installed-apps` and `installed-packages` list component and package IDs, system ones included, with no version or title; `vpm list packages` is the same with a `package ids:` header. `vpm info <package> --package` is text: title, version, build number, install and update time in GMT, `installer id` (`com.amazon.package-manager.cli` for side-loaded packages, `com.amazon.venezia|<content id>` for Appstore ones, `…package-manager.service` for system ones), component IDs. `version:` can be empty (a system library on a stick). `vpm info --package <component>` prints the package that owns the component. `vpm list packages | tail -n +2 | xargs -n1 vpm info --package` returns every package in one round trip: about 1 s for the Virtual Device's 40 packages, but 31 s for a stick's 115 (one call takes about 0.25 s there). `xargs -P4` cuts that to 5 s but interleaves the blocks, so OVD writes each to its own file in a `mktemp -d` folder and prints them in ID order. `vpm info` on an unknown ID exits 248 with `no info available`.
- `vlcm list` is a fixed-width table of running components (pid, state such as `VISIBLE` or `READY`, lifespan such as `PERMANENT`, container); with `--app-id` of an app that isn't running, or isn't installed, it prints the header only. Right after `launch-app` a stick lists the app `IDLE` with pid 0 and an empty container, and `READY` with a pid 0.6 s later; with the container column empty, OVD's whitespace split reads the launch-args column (`<none>`) there. pid 0 isn't running. App processes don't show in the device's `ps`, so nothing reports how long an app has run.
- `vega device is-app-installed` and `is-app-running` exit 0 either way; only the text differs. `is-app-installed` needs the component ID: with a package ID it says "not installed". `launch-app` and `uninstall-app` also accept the package ID (launch then starts the main component); `vlcm terminate-app` and `vpm … --package` take package IDs.
- `vega device launch-app` runs `vpm list packages`, `vlcm terminate-app --force --pkg-id <package>` and `vmsgr send pkg://<component>`: it always restarts the app, and a relaunched app gets a new pid. It prints `Sending: pkg://<id>` (2 s on a stick, 1 s on the Virtual Device); once it returned 87 s after the app was up, waiting on the SDK's telemetry step. `vega device terminate-app` is a force stop with no graceful mode: it prints `Force stopping pkg: <package>` and exits 0 either way. `vlcm terminate-app --pkg-id <package>` without `--force` is the graceful one: it exits 0 with `Stopping pkg: …` when the app runs, and **255** with `Stopping pkg: …` and `Failed to stop app` when nothing runs or the package isn't installed. With `--force` it exits 0 with `Force stopping pkg: …` whatever the state.
- `launch-app` and `uninstall-app` exit 3 with `Failed: App could not be determined` for an app that isn't installed, and 2 with `Device not found: …` for a `--device` that isn't connected (the same text as `install-app`). Uninstall takes 4 s on a stick and 1 s on the Virtual Device; afterwards `vpm info <package> --package` exits 248.
- Installing over a running app stops it, and it isn't started again. Uninstalling a running app works. The data path `vpm info <component>` reports (`/home/app_user/packages/<package>/data`) isn't visible to the shell user. On a stick (2026-11-08), uninstalling and installing again cleared the app's data, while installing over the installed app kept it.
- `vlcm crash-history` has no JSON mode. It prints `AppCrashInfoBuffer:` with `Capacity: 10` and `Size: N`, then up to 10 entries (its capacity), one per crash, newest first, of every package, system ones included: pid, packageId, timestamp (device uptime), version, buildNumber, hadCompInFg and metadata (`LCM_KILLREASON` empty, `LCM_KILLTIME` in UTC with its epoch ms). Entries survive an uninstall. An entry is there about 1 s after `launch-app` returned. Why a crashing launch has once shown no entry at all is unexplained; OVD then reports the launch as not running.
- `loggingctl vault --ls SYSTEM_TOMBSTONE/acr` prints JSON (`artifacts`, `status`), not sorted, one name per crash report: `<index>#crash_<epoch s>_<uid>_<gid>_<pid>_<signal>_<package, dots as _>.acr`. A report is enrolled about 0.6 s after the crash. `loggingctl vault --cat SYSTEM_TOMBSTONE <index>` of a package that is no longer installed prints `Insufficient permissions` with status -7, and an unknown index `No entry found for tag …` with status -8; both exit 0.
- A crash report (ACR) is about 350 KB: a `Key: Value` header (`CrashLang`, `CrashReason`, `Process`, `Source`…), the JS stack in a `<non_native_stack_trace>` section, then meminfo, a minidump and a core dump. OVD reads only the header and the stack, through `sed -n -e "1,/^\$/p" -e "/<non_native_stack_trace>/,/<\/non_native_stack_trace>/p"` on the device.
- The stick's journal rotates fast enough that a crash right after launch is gone from it moments later, so only a log capture running during the launch catches the crash's lines (the app's own JS error, logged in Release too, the `acr_core_dump` "crashed with signal 6" line and the LCM death line).
- A background capture survives the `vda shell` call that started it: `f=$(mktemp)`, then `timeout <s> loggingctl log -f -o short_precise > "$f" 2>&1 &`, then `echo "$f $!"` prints the file and the `timeout` pid in 0.6 s. `kill <pid>` alone leaves `loggingctl` running as an orphan; `pkill -P <pid>` ends it, and `timeout` ends both if nothing stops them. Device temp files are in a 476 MB tmpfs. The device has Toybox `timeout`, `pkill`, `sed` and `grep`.
- Right after `vega virtual-device start` reports ready, VDA can drop the Virtual Device for a few seconds (`vda: device 'emulator-5554' not found`) and list it again under a new transport ID.

## 9. Testing

- Vitest in every package; tests mirror `src/` under each package's `test/`.
- No hardware, SDK, network or real timers in tests. Core uses a fake runner that replays fixtures from `fixtures/<sdk-version>/`.
- Fixtures are sanitized with the neutral sample data (ADR 0016).
- CLI tests assert `--json` output and exit codes. No snapshot tests.
- End-to-end tests (`e2e/`, `pnpm run test:e2e`) run the built CLI and desktop app against a fake SDK that answers only with recorded fixtures (ADR 0023). They check user flows, the SDK commands run and the state left behind. CI runs them as the required `e2e` job.
- Real-device behavior is checked manually. The nightly SDK job (Stage 3.7, not built yet) will cover the Virtual Device (ADR 0007).
